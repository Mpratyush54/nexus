# Live Agent Steering — Decisions

Date: 2026-09-17
Scope: `internal/steering/steering.go` for nexus issue #22 (Live Agent
Steering, Interruption & Intervention).
Status: implemented stdlib-only; `go build ./...`, `go vet`, and `go test`
cover the new package.
Wire mapping: steering reuses the `internal/server/ws.go` envelope —
clients send `{type:"action", event_type:<steering event>}`, the daemon fans
out `{type:"event", event_type:<steering event>}` via `Hub.PublishEvent`.
No new envelope types were added, so `ws.go` is untouched.

## Decision 1 — cancel-token (context + Done channel), not thread-kill

Why:
- Go has no safe way to kill a goroutine mid-tool-call, and the daemon
runner is a separate process the hub cannot preempt anyway. The portable
primitive both sides already understand is cancellation: `RequestInterrupt`
cancels the run's `context.Context` and closes its `Done` channel, so a
pending tool call written as `select { case <-mgr.Done(id): abort … }` or
`<-'ctx.Done()` stops at its next cancellation check instead of running to
completion.
- The same call collapses the two production signals behind one seam: the
`DaemonBridge.Signal` stub is where a real deployment sends SIGINT to the
runner process or delivers a cancellation token over MCP. The state machine
does not care which transport fired — it only needs "runner told to stop",
which keeps unit tests process- and socket-free (a `RecordingBridge`).
- Resume re-arms a fresh context + open `Done` channel rather than "uncancelling"
(the old ones stay cancelled by design), so a stale `select` from before the
pause can never un-block the resumed run by accident.

## Decision 2 — single-steerer lock + per-owner FIFO queue

Why:
- Two spectators typing conflicting corrections ("revert the migration" vs
"keep going") must never interleave: whichever steerer interrupts first
becomes the run's `owner`, and every `RequestInterrupt` / `Steer` / `Resume`
from anyone else fails with `ErrSteerConflict`. Rejection beats merging —
an agent cannot obey two contradictory redirections at once, and silently
picking one would hide the conflict from the loser.
- One global mutex serializes all transitions (deadlock-free, no lock
ordering), while ownership is per-run so independent sessions steer
concurrently. Same-owner prompts queue FIFO instead of replacing each other,
because a correction often arrives as a burst ("stop … now use X … and add
an index") whose order matters.
- Resume is owner-only and clears the owner, releasing the lock; there is no
timeout eviction in this slice (a stuck steerer blocks the run visibly in
`StatePaused`, which the UI surfaces, rather than being silently overridden).

## Decision 3 — priority injection before the next tool call

Why:
- Alternatives were (a) appending the correction to the normal message log
(where it races the already-planned tool call) or (b) restarting the run
(which loses tool progress). Priority injection is the middle path: `Steer`
queues the prompt, and the agent contract requires `TakeNextPrompt` (after a
`Gate` check) before every tool call, so the correction is prepended to the
model context as a high-priority instruction ahead of whatever the next tool
call would have been.
- `Gate` returning `ErrPaused` while paused makes "paused" a hard stop, not
advisory: tool execution is forbidden until `Resume`, but prompt ingestion
still works, so the corrected course is loaded before the first post-resume
tool call.
- Events (`AGENT_INTERRUPT_REQUESTED` / `AGENT_PAUSED` / `AGENT_STEER_PROMPT`
/ `AGENT_RESUMED`) are recorded as an ordered ledger per run for WS fan-out,
so every spectator's UI replays the same pause → steer → resume sequence the
state machine enforced.
