# Copy-on-Write Memory Branching — Phase 5 Decisions

Date: 2026-09-17
Scope: `migrations/005_branches.*`, `internal/store/branches.go` (+
`branches_test.go`) for nexus issue #17 / implementation-plan.md §5.1–§5.2.
Status: implemented against `MemStore` (+ `PostgresStore` SQL paths, no live
DB in CI); covered by fork/diverge/read-resolution/write-isolation tests.

## Decision 1 — Copy-on-Write instead of copy-on-fork

Why CoW: a fork inserts exactly one `memory_branches` row and zero memory
rows. Branching is O(1) no matter how large the project memory grows, and
there is no snapshot garbage to reconcile — the parent's rows ARE the
child's inherited state until the child overwrites a key. This matches the
git mental model called out in the plan's locked decisions and keeps the
fork path free of transactional bulk-copy hazards (partial copies,
sequence gaps, embedding duplication).

Consequence: storage cost is proportional to divergence, not to branch
count. The trade-off is read-time chain walking (bounded: ≤ 5 levels, one
indexed lookup per level), which is cheap next to the embedding search that
follows it.

## Decision 2 — Parent pointer, not branch snapshot or key namespacing

Why a `parent_branch_id` pointer: resolution is a pure walk
(child → parent → … → main, first key match wins) with no data movement at
fork, diff, or merge time. Alternatives rejected:

- Full snapshot copy at fork: O(n) writes per fork, stale the moment the
  parent advances, and every fork doubles embedding storage.
- Key namespacing (`branch:key` prefixes): leaks branching into every query
  in the codebase (search, promotion, materializer) instead of containing it
  in one resolution function, and makes "diff against main" a string-parsing
  exercise.

The pointer also gives lineage for free: staleness detection (plan §5.4 —
"parent updated a key the child also has") is a comparison of two
resolution results, and merge (issue #18) is "replay source-only rows onto
target as PROPOSED".

Depth is capped at 5 levels (plan §5.4) and enforced in `ForkBranch` on both
backends, so chains can never degrade into linked-list abuse. Cycle guards
ride along because a self-parented row would otherwise loop the resolver.

## Decision 3 — Every project gets a shared "main" automatically

Why auto-main: `ResolveRead` needs a well-defined chain root — "walk to
main" is meaningless if main may not exist. Seeding it in two places covers
both timelines: the migration backfills `main` (shared) for every project
that already exists, and `EnsureMainBranch` get-or-creates it for projects
born afterwards. Branch writes force `project_id` to the branch's project,
so an item can never dangle on the wrong project's chain.

Why shared: main is the convergence point — Bob's agent must inherit
Alice's confirmed project memories without an access grant. Privacy lives
on the leaves: personal/feature branches default to `private`
(`CheckBranchAccess`: owner or system only), and only their owner can read
them. Episodes stay project-scoped and unbranched (plan §5.3).

## Single-file constraint (no edits to existing store files)

`branches.go` touches no existing file (verified: no `MemoryBranch`,
`BranchID`, or `branch_id` symbol existed). To honor that:

- `MemoryItem` gains no `BranchID` field. The Postgres path tags rows via
  the `branch_id` column using the id passed to `WriteToBranch`, and
  `ResolveRead` re-fetches winners by id through the existing
  `GetMemoryItem`. The MemStore path keeps branch overlays in a sidecar
  bucket keyed by store instance, physically separate from main-line
  memories — which is also what makes "fork copies zero rows" literally
  true in tests.
- The one deliberate duplication: per-level `SELECT id … WHERE branch_id`
  lookups instead of extending `memoryColumns`. If a later change adds a
  `BranchID` field to `MemoryItem`, this file's scanners collapse into the
  shared ones with no behavior change.
