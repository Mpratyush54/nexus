# Security Hardening — Decisions (2026-09-17)

Issue: Mpratyush54/nexus#19 — `[Phase 6] Security Hardening, Path Traversal
Audit & Secret Scanners`. Scope (strict): `internal/security/hardening.go`
(new package) + `internal/security/hardening_test.go` + this doc.
`internal/daemon/fileops.go` untouched; the tests prove the existing sandbox
holds rather than changing it. Plan refs: §6.1 Security, §6.4 Rate Limiting.

---

## 1. Two-layer path defense: strict lexical pre-check + kernel-truth sandbox

- **Context:** `daemon.SecureJoin` already canonicalizes through the kernel
  (deepest-existing-ancestor resolution, `GetFinalPathNameByHandleW` on
  Windows for junctions) and is proven by 17 passing tests. The issue asks for
  an adversarial suite (`..`, symlinks, ADS) plus two new classes (`//`,
  trailing dots) without touching `fileops.go`.
- **Decision:** Add `security.ValidatePath` (stdlib-only, no I/O) in front of
  `SecureJoin` (authoritative, does I/O), plus `security.AdversarialCases()`
  as the single shared corpus both layers are tested against.
- **Alternatives:** (a) Edit `SecureJoin` to also reject `//`/trailing dots —
  forbidden by issue scope, and conflates policy (reject confusing names)
  with mechanism (contain escapes). (b) A lone regex filter — cannot see
  symlinks/junctions, the actual escape vector.
- **Why:** Defense in depth with a clean seam: `ValidatePath` gives cheap,
  clear, cross-platform rejections for everything lexical (NUL, blank, `:`,
  absolute, `..` segment, `//`, trailing dot/space); `SecureJoin` remains the
  only component allowed to answer symlink/junction questions because only it
  talks to the kernel. The corpus test asserts `ValidatePath` rejects 100% of
  lexical classes (symlink names excluded — innocent until resolved)
  and `SecureJoin` never lets any case escape (rejected, or resolved inside).
- **Consequences:** Callers should run `ValidatePath` first, `SecureJoin`
  second. `ValidatePath` is deliberately stricter than the filesystem
  (`sub//file` and `hello.txt.` are rejected even though they resolve
  inside) — anyone with a legitimate double-separator path must `Clean` it
  first and retry.

## 2. Secret enforcement fails closed on `scan.NeverPatterns`

- **Context:** Plan §6.1 and issue scope demand `NeverPatterns` (API keys,
  tokens, SSH keys) block reads/writes of credentials.
- **Decision:** `security.EnforceSecret` / `ContainsSecret` wrap the exact
  same `scan.NeverPatterns` the daemon uses; any single match returns
  `ErrSecretBlocked`, empty input passes, matched content is never returned.
  The wrapper test mirrors the daemon's own `TestSecretFailClosed` semantics
  (blocked write never lands on disk; seeded secret file unreadable).
- **Alternatives:** (a) Fork a new pattern list in `security` — drifts from
  the reviewed vocabulary on the next pattern update. (b) Fail-open with a
  warning log — leaks credentials into agent context on the first miss.
- **Why fail-closed:** Secrets are a one-way door: a single leaked key in an
  agent transcript, embedding, or event payload cannot be un-read. Blocking
  (refuse the op, return no content) bounds the blast radius to a retryable
  error; warning-and-continuing bounds it to nothing. Reusing the daemon's
  vocabulary guarantees both layers agree on what "secret" means.
- **Consequences:** False positives block legitimate ops (mitigated upstream
  by the long-token requirement on the `api_key` pattern). Any new
  `NeverPatterns` entry automatically tightens both layers — no second list
  to sync.

## 3. Branch visibility enforced at the store layer

- **Context:** Plan §5.1 defines `memory_branches.visibility IN
  ('private','shared')`; §6.1 requires enforcement at the store layer.
- **Decision:** `security.CanAccess(viewerID, ownerID, visibility)` helper:
  owner always passes; others pass only on `shared`; empty viewer
  (anonymous) never passes; `NormalizeVisibility` maps unknown/empty to
  `private`. `EnforceBranchAccess` is the error form (`ErrNotAuthorized`).
- **Alternatives:** (a) Enforce only at the HTTP edge — every future route
  (WebSocket fan-out, episode search, materializer) must remember to check;
  one miss exposes private branches. (b) SQL `RLS` policies — Postgres-only,
  untestable in `MemStore`, invisible in code review.
- **Why store layer:** It is the narrowest choke point every read path
  already funnels through (`memory.go`, branch resolution, search). A Go
  helper is backend-agnostic (MemStore and Postgres share it), unit-testable
  without a database, and reviewable beside the queries. Fail-closed
  normalization means a typo'd visibility (`'prviate'`) restricts instead of
  publishing.
- **Consequences:** Store methods must actually call it on every
  branch-scoped read (follow-up wiring, outside this scope). Shared means
  "any authenticated project member", not "public" — true public sharing
  needs a separate capability, never the absence of a check.

## 4. Rate limiting: stdlib token bucket, 100/s events + 50/s fileops

- **Context:** Plan §6.4: events 100/s per project; daemon file ops 50/s.
- **Decision:** `security.Limiter` — mutex + `time.Now` token bucket, no deps;
  `NewEventLimiter()` (100/100) and `NewFileOpsLimiter()` (50/50) presets.
  `Allow` consumes one token; exhaustion returns false (caller drops/queues,
  never admits). Non-positive rate/burst clamp to 1; non-positive `AllowN`
  is rejected.
- **Alternatives:** (a) `golang.org/x/time/rate` — correct but a new
  supply-chain dependency for ~30 lines of logic; the daemon must stay
  minimal. (b) Fixed-window counters — admit 2× bursts at window edges and
  need a reaper goroutine. (c) Per-limiter goroutine ticker — leaks
  goroutines per project.
- **Why token bucket:** Smooths bursts (a 100-burst deploy spike passes, a
  sustained 200/s loop is throttled to 100/s) with O(1) lazy refill on the
  hot path — no background goroutines, no timers, trivially race-testable.
  Burst == rate gives each limiter a one-second burst budget, the standard
  reading of "N/s" caps.
- **Consequences:** One `Limiter` instance per scope (per-project events,
  per-daemon fileops); sharing one global limiter would throttle unrelated
  projects. Refill uses wall-clock `time.Now` (monotonic) — test sleeps are
  bounded (~200ms) and assert ranges, not exact counts.
