# Developer CLI Client (`cmd/nexus`) — 2026-09-17

Issue: Mpratyush54/nexus#21 (`[CLI] Developer CLI Client (cmd/nexus)`).
Scope: `cmd/nexus/` only. The `mem` skeleton in `./main.go` was read for
context and left untouched.

## Decision 1 — new `cmd/nexus` package instead of extending `mem`

Why:

- `./main.go` is the locked Phase 1 single-user skeleton (`projects`,
  `status`). The plan's target tree already reserves a separate CLI
  entrypoint (`cmd/.../main.go`); growing the skeleton in place would tangle
  single-user leftovers with the multiplayer control-plane client.
- A fresh package lets the CLI speak the Phase 1.8 server API
  (`/healthz`, `/memory`, `/memory/search`, `/episodes`, `/episodes/search`,
  workspaces) with no coupling to `internal/project`'s local-only model.
- Migration path is explicit, not accidental: Phase 1b can re-point `mem
  recall` / `mem remember` at this client (or vice versa) once import data
  lands, instead of inheriting behavior through shared code.

## Decision 2 — stdlib only (`flag`, `net/http`, `encoding/json`, `text/tabwriter`)

Why:

- `go.mod` is dependency-free (`central-memory, go 1.26.1, zero deps`) and
  every prior decision doc defers new deps to the Postgres/daemon phases.
  The CLI needs none: `net/http` covers REST, `encoding/json` covers the
  envelope, `flag` covers subcommand parsing, `tabwriter` covers tables.
- `flag` with `ContinueOnError` + discarded output keeps parsing pure and
  testable: every `parse*Args` returns `(options, error)` and never calls
  `os.Exit`, so arg-parsing tests run without subprocesses.
- No cobra/bubbletea: five command groups with stable, scriptable output do
  not justify a framework or an interactive TUI.

## Decision 3 — `text/tabwriter` tables + `--json` flag

Why:

- Humans get aligned columns via `renderTable` (a pure function over
  headers+rows, unit-tested in `client_test.go`); machines get `--json`
  (global, plus per-subcommand acceptance so `nexus memory search --json …`
  works regardless of flag position).
- `truncate` collapses whitespace and caps cell width so one long memory
  cannot blow up a terminal table; JSON output is never truncated.

## Decision 4 — stubs that call the server, graceful Phase-tagged errors

The Phase 1.8 server implements only health, workspaces, memory
create/search, and episode create/search. The issue still requires session
and branch commands plus memory moderation, so the CLI:

- Implements `memory search` / `propose`, `episode list` / `search`, and
  `status` against real routes today.
- Implements `memory confirm` / `reject` (`POST /memory/{id}/confirm|reject`),
  `session list|create|join` (`/sessions…`), and
  `branch list|fork|checkout|diff|merge` (`/branches…`) as calls to the
  routes those phases will add (Phase 2 confirmation, Phase 3 sessions,
  Phase 5 branching per `migrations/005_branches.up.sql`).
- Maps upstream 404/405 to `errNotImplemented{Feature, Phase}` → stderr
  `not implemented: …` + exit code 3, distinct from usage errors (2) and
  runtime failures (1). No raw HTTP dumps for known-future routes.
- Decodes stub responses into `map[string]any` with the `strField` helper
  instead of strict structs, so tables survive future server shape changes.

Endpoint contract the CLI assumes ( Branches/sessions/confirm-reject rows
are the proposed Phase 2/3/5 API ):

| CLI command      | Method + path                    | Server state |
|---|---|---|
| `status`         | `GET /healthz`, `GET /workspaces/{id}/active` | live (1.8) |
| `memory search`  | `GET /memory/search`             | live (1.8) |
| `memory propose` | `POST /memory`                   | live (1.8) |
| `memory confirm` | `POST /memory/{id}/confirm`      | Phase 2 (stub) |
| `memory reject`  | `POST /memory/{id}/reject`       | Phase 2 (stub) |
| `session …`      | `GET/POST /sessions…`            | Phase 3 (stub) |
| `branch …`       | `GET/POST /branches…`            | Phase 5 (stub) |
| `episode …`      | `GET /episodes/search`           | live (1.8) |
| `doctor server`  | `GET /healthz` (no auth)         | live (1.8) |
| `doctor daemon`  | `GET {daemon}/git/status`        | live (daemon core) |
| `doctor git`     | local `git rev-parse` / `status` | local |

Other notes:

- Level filtering for `memory search --level` is applied client-side until
  the server gains a level parameter (the flag is also forwarded for
  forward-compat). `episode search` sends the query as both `q` and
  `error_pattern` so one call covers narrative and pattern matches.
- Config resolution: flags > `NEXUS_*` env (`NEXUS_SERVER`,
  `NEXUS_TOKEN`/`CENTRAL_MEMORY_TOKEN`, `NEXUS_DAEMON`,
  `NEXUS_DAEMON_TOKEN`, `NEXUS_PROJECT`) > built-in defaults. Daemon auth
  falls back to `<cwd>/.central-memory/daemon.token`.
- `doctor` always prints its probe table, then exits 1 naming the failing
  probes so scripts can gate on it.
